# AGENTS.md

Guidance for AI coding agents working in this repo, whatever harness or model
drives them. This file is the single source of truth for build commands,
conventions, design invariants, and non-goals. Read the "Design invariants" and
"Non-goals" sections before changing core flow — many "obvious improvements"
are explicit non-goals.
`docs/architecture.md` holds the diagrams; `docs/TODO.md` is a historical review
log, not instructions.

## Agent usage policy

This file assumes nothing about the harness, tool, or model driving you. Use
whatever delegation your environment provides; if it provides none, do the
work yourself.

- **Delegate substantive work when a suitable agent exists.** Parallel
  research, review, and scoped implementation are good candidates. Pick the
  agent whose role matches the task (implementation, review, testing, UI); if
  none matches, do the task yourself.
- **Partition work by file** (see below) when dispatching multiple agents.
- **Verify every delegate's work yourself** — run the build and the tests. A
  subagent's summary is not evidence.
- **Read `AGENTS.md` before starting** — this file is the single source of truth
  for build commands, conventions, and boundaries.

## Multi-agent coordination

When dispatching multiple agents in parallel, partition work by **file
ownership** to prevent edit conflicts:

- **Agents work only inside the project root directory.** Don't read or write
  outside the repo workspace, with one exception: the read-only NanoLedger
  reference clone above may be read, never written.
- **One file, one owner.** Each file is owned by exactly one agent for the
  duration of the task. No two agents may edit the same file concurrently.
  Assign every target file to a single agent in the task prompt.
- **Partition by file, not by region.** Don't ask two agents to edit different
  regions of the same file (e.g., "agent A owns the top bar, agent B owns the
  bottom bar" of one screen). Region-level splits cause merge clobbering and
  dropped imports — partition at the file level instead. If two features touch
  one file, one agent does both.
- **Shared helpers go to one owner.** If both agents need a new shared
  composable/util, assign its creation to exactly one agent; the other consumes
  it read-only or waits for it to land.
- **State the ownership map in each task prompt.** Explicitly list which files
  each agent may edit and which are off-limits.

## Build & environment

**Use devenv, or do nothing. No workarounds.**

- Run every build, test, and device command through the dev shell:
  `devenv shell -- <command>` (or enter it, then run the command). Nothing
  else counts as a build. If devenv will not start, stop and say so — do not
  find another way to run Gradle.
- **Never go into the Nix store.** Never read, invoke, or point anything at
  `/nix/store/...` — no `JAVA_HOME`, `PATH`, `sdk.dir`, aapt2, or tool path
  taken from there and handed to a command by hand. The shell sets up everything
  a build needs; if something is missing or wrong, fix it in `devenv.nix` /
  `devenv.yaml` (ask the user first) or report it.
- **Don't export or hand-set environment variables** to compensate for a broken
  or missing shell setup — no `GRADLE_USER_HOME`, `GRADLE_OPTS`, `ANDROID_*`,
  ad-hoc `PATH` prefixes, or wrappers around tools. Ask the user before adding
  an export to `devenv.nix`.
- Single-module Android app (`:app`), Kotlin + Jetpack Compose. JDK 17, AGP
  8.1.4, Kotlin 1.9.22, Compose compiler 1.5.8, compileSdk/targetSdk 34,
  minSdk 26.
- Dev environment is managed by [devenv](https://devenv.sh) (Nix).
  **`local.properties` is auto-generated by nix-shell** and gitignored — never
  commit or hand-edit it; its `sdk.dir` points into the Nix store and is
  machine-specific.
- Enter the dev shell with `devenv shell`. Exposes scripts: `build`
  (`./gradlew assembleDebug`), `install` (`./gradlew installDebug`), `clear`
  (wipes `local.properties` — use if SDK path is stale).
- SDK / build-tools come from `devenv.nix`. Don't install via Android Studio's
  SDK Manager without updating `devenv.nix`, or paths will drift.
- `enterShell` also exports two Gradle settings an agent must not "simplify"
  away: `GRADLE_USER_HOME="$PWD/.gradle-user-home"` keeps Gradle's wrapper,
  daemon, and caches inside the repo (gitignored) instead of `~/.gradle`, and
  `GRADLE_OPTS` points AGP at the SDK's `aapt2`. AGP downloads a
  generic-Linux aapt2 from Maven that NixOS refuses to start without `nix-ld`;
  the SDK build-tools copy is patched by nixpkgs and runs. Without it, any build
  that actually executes `processDebugResources` (clean build, resource change,
  `--rerun-tasks`) fails with "Could not start dynamically linked executable",
  even though warm-cache builds pass. Use `$ANDROID_HOME`, not
  `ANDROID_SDK_ROOT` — the android module only exports the former.
- No pre-commit hooks. CI (`.github/workflows/android.yml`) runs
  `assembleDebug testDebugUnitTest` on pushes and PRs to `develop` and
  `master`, and builds a signed release APK on `v*` tags. Run the build and the
  tests locally before pushing — CI is a backstop, not the first check.

## Device etiquette (the user runs their coding agent on the same phone)

- **Never send adb input events (`input tap` / `input text` / keyevents) without
  the user preparing for it.** The phone is in active use; blind input has
  landed in the user's editor before. Always guard inputs with a focus check
  (`dumpsys window | grep
  mCurrentFocus`) and abort if the app isn't focused.
- **Screenshot protocol:** first output one line like "In ~5 seconds I will take
  a screenshot — switch to the app", wait ~10 s (sleep in the same command),
  capture only if `mCurrentFocus` is `org.notifledger.app`, then **bring Termux
  back to the foreground**
  (`am start -n com.termux/com.termux.app.TermuxActivity`) so the user knows the
  screenshot is done.

## Commands

- Build: `./gradlew assembleDebug`
- Run JVM unit tests: `./gradlew testDebugUnitTest` (release variant:
  `testReleaseUnitTest`)
- Single test class:
  `./gradlew testDebugUnitTest --tests "org.notifledger.app.parser.ParserEngineTest"`
- Single test method:
  `./gradlew testDebugUnitTest --tests "*.ParserEngineTest.parse*"`
- Install on device: `./gradlew installDebug`
- No `lint`/`detekt`/`ktlint` is configured. AGP's built-in
  `./gradlew lintDebug` runs but is not part of the CI workflow, so nothing
  gates on it.

## Tests

- Tests are **JVM unit tests only** (`app/src/test/...`, plain JUnit 4). No
  Robolectric, no MockK/Mockito, and `app/src/androidTest` is empty — there are
  no instrumented tests.
- Anything needing Android framework classes must be unit-testable without a
  device, or restructured. Don't assert on `Context`/`Uri`/framework types in
  unit tests without adding Robolectric first.
- Test packages mirror `main`: `parser`, `journal`, `notification`, `settings`,
  `filters`, `log`, `stats`, `ui`, and `ui/components`.

## Architecture (deliberately non-standard)

NotifLedger turns bank/payment notifications into [hledger](https://hledger.org)
journal entries automatically. Core stance: if a bank told you it happened,
don't make the human confirm it.

- **No DI framework.** Manual construction in `NotifLedgerApp` (the
  `Application`). Don't introduce Hilt/Koin — it's an explicit non-goal (see
  Non-goals).
- **No Room / database.** State lives in the hledger journal file (via Storage
  Access Framework `content://` URIs) and app settings in DataStore Preferences.
  Don't add a DB "to cache things" — that's a non-goal.
- **`JournalWriter` is pure** — no file I/O. The UI ViewModels read/write
  through `JournalRepository` (Android's `ContentResolver`). Keep I/O out of
  `JournalWriter`; it's tested as a pure text formatter and that boundary
  matters.
- **`NotifLedgerApp` settings getters are `suspend`** — the `NotifListener` path
  runs on a coroutine (`Dispatchers.IO`), so there is no `runBlocking` on it.
- **Parser stays a generic heuristic**: prefers the number next to a currency
  marker (`kr`, `NOK`, `€`, …), skips card masks (`*1234`) and dates, falls back
  to the first parseable number in the body, then the title; title = payee.
  Norwegian decimals (`184,50`) and grouped amounts (`1.234,56`, `1 234,56`)
  are handled. Whitespace-separated digit groups merge only when they read as
  thousands blocks, so `1234 184,50` is a mask or reference number plus 184.50
  rather than 1234184.50. Do **not** add per-bank parser config — explicit
  non-goal (see Non-goals).
- KSP plugin is declared in root `build.gradle.kts` but **not applied in
  `:app`** (no Room/Hilt/Moshi). Don't assume KSP annotations work without
  applying the plugin.

## Design invariants

The journal file is plain text, append-only, diffable and git-friendly. Nothing
in the app may compromise that: the journal file (SAF `content://` URI) is the
only source of truth for transactions, settings live in DataStore, and there is
no cache/DB in between. Two paths write the same journal, immediately, with no
approval step:

- **Notification path:** capture (allowlist) → generic parse → categorization
  rules → default payment account fills the money leg → append. A parse with no
  number still posts best-effort (title as payee, empty amount auto-balanced) —
  never gated, never dropped. Mistakes are fixed after the fact on the main
  list.
- **Manual path (quick-add):** amount, payee, account (pre-filled from the
  default payment account, overridable); currency/date default to now/base
  currency. Manual and notification entries are the same `Transaction` type and
  indistinguishable once written.

Consequences worth keeping:

- Filter capture by a **user-selected package allowlist** — never global
  capture. Store only what parsing needs (title, text, package, timestamp); raw
  notification text is never logged or persisted.
- The **default payment account** is a per-entry starting value, not a hard
  constraint. Changing it in Settings affects new entries only, never past ones.
- **Categorization rules** are an ordered YAML list, first regex match wins,
  fallback `expenses:unknown`. The listener uses a cache loaded at process
  start, so rule edits apply to the next notification after the app process
  restarts.
- **Backups** (the one deliberate exception to "no in-app copy"): a timestamped
  `backups/journal_backup_<ts>.txt` is written before each journal overwrite,
  newest 10 kept, excluded from Android cloud backup and device transfer, and
  only ever consulted by hand — never merged back automatically.
- The **raw journal screen is read-only**; edits go through the main list (or an
  external editor), so the app needs no raw-hledger text-editing UI.
- Low-confidence parsing still beats a confirmation gate: accepting
  easy-to-find, easy-to-fix mistakes is the point, not a bug to close with a
  review step.

## Non-goals

Don't "fix" these; they are deliberate. A change needs a new explicit
instruction.

- No bank API / Open Banking — notifications only, to avoid credential/OAuth
  surface.
- No cloud backend — sync is whatever the user already uses for the journal
  file.
- No auto-categorization via ML — rule-based stays legible and debuggable.
- No per-bank parser rules — the generic heuristic above is enough.
- No DI framework (Hilt/Koin) — manual construction in `NotifLedgerApp`.
- No Room/database or cache layer — journal file + DataStore only.

## Deliberately skipped (accepted residuals)

From the completed review rounds in `docs/TODO.md`; don't reopen without a new
instruction:

- `MainViewModel.simulateNotification` bypasses categorization rules and
  hardcodes `expenses:unknown`; `NotificationHandler.DEFAULT_EXPENSE_ACCOUNT`
  stays separate.
- No read-back verification after SAF writes; backups can degrade if the user
  keeps writing after a failed write.
- Repository text transforms run on `Dispatchers.IO` — fine at current journal
  sizes; revisit if multi-MB journals appear.
- `Channel.UNLIMITED` in the listener (correctness over bounded memory at this
  app's event rates) and a backup write on every overwrite (deliberate recovery
  point).

## Notification flow

- `NotifListener` extends `NotificationListenerService` (manifest-declared,
  protected permission) — the core entry point, wired in `AndroidManifest.xml`.
- Capture is **allowlist-filtered by package name** (user-selected apps), not
  global. Allowlist lives in DataStore via `SettingsManager`.
- `BIND_NOTIFICATION_LISTENER_SERVICE` is a protected permission — the user must
  grant it in system Settings (Notifications → Notification access). Nothing
  in-app can grant it silently; don't try.
- `NotificationHelper.showListeningNotification` posts a persistent
  foreground-style notification on startup — required to keep the listener
  alive, don't remove it.

## Coding standards

Simple beats clever, always. If a reviewer has to pause and think "wait, what
does this do", rewrite it — even if it works. Code is read far more often than
written; optimize for the next reader, including future you. These rules are the
source of truth.

**One function, one action, one thing**

- A function does exactly one thing. If you describe it with "and", split it.
- A function fits on one screen; prefer many small named functions over one
  large function with comments marking "sections".
- Max ~3 levels of nesting (if inside if inside loop) — extract the inner logic
  or invert the condition.
- Max 1000 lines per file. No file should require scrolling to understand its
  purpose.

**Don't repeat yourself**

- Duplication is the default thing to remove in this repo. **The same line
  appearing two or three times in a file, unchanged, means something is wrong** —
  pull it into one named function or value and call it from each site.
- Lines that repeat with only a literal changed (`A -> f(x)` / `B -> f(y)`) are
  duplication too: write one function that takes the changed part. If the
  `when` arms of a new enum entry would be copy-paste of an existing arm, the
  data belongs in the enum instead of in another branch.
- A repeated *shape* with genuinely different logic is not duplication —
  exhaustive `when` branches, one row per column/field, and distinct error
  messages are fine when the bodies differ. Don't force them into an
  abstraction.
- A helper earns its name when the same logic would otherwise live in 2+ places
  at once, or the repetition is inside one file — extracting a duplicate is not
  the "abstraction layer" the next section warns about. Shared helpers used by
  two files have one owner (see Multi-agent coordination).
- Prefer fewest copies over fewest lines: a little repeated boilerplate that
  stays readable beats a clever parameterized helper, but "it was quicker to
  paste" is never the reason.

**Simple beats clever**

- Write the dumbest version that works; optimize measured, not guessed.
- No abstraction layers, factories, or indirection until 3+ concrete cases need
  them. Don't build for a future that might not come.
- Prefer explicit over implicit; magic (metaprogramming, hidden side effects,
  global mutable state) is a last resort.
- If you can delete code and nothing breaks, delete it.

**Naming**

- Names say what a thing _is_ or _does_, not how it's implemented.
- No abbreviations unless universally obvious (`id`, `url`, `i` in a tight
  loop).
- Booleans read like yes/no questions (`isActive`, `hasPermission`, `canRetry`);
  functions are verbs (`sendEmail`), values are nouns (`emailAddress`).

**Functions & data**

- Pure functions by default: same input, same output, no hidden state mutation.
  Side effects (I/O, network, writes) live in clearly named, isolated functions
  — never buried in "helper" logic.
- Don't mutate arguments; return new values.
- Prefer a few explicit parameters over a giant options object.

**Comments**

- Comments explain _why_, never _what_. If the _what_ isn't obvious, rewrite the
  code — don't caption it. Delete commented-out code; that's what git history is
  for.

**Errors**

- Fail loudly and early. No silent catches that swallow errors. (Note:
  `NotifLedgerApp` catches-and-defaults in a few blocks — deliberate boundary
  fallbacks, not a pattern to spread.)
- Handle errors at the boundary where you have enough context to act; no
  catch-and-rethrow for no reason.

**Structure**

- Feature-based package structure, not type-based: `parser/`, `journal/`,
  `notification/`, `ui/`, `model/` — group by what code _does_, not by
  `controllers/`/`models/`/`views/`.
- Code grows vertically and in depth(more functions, more files), not
  horizontally (more nesting, more indentation).

## Before opening a PR

1. Could someone unfamiliar with this code understand it in one read?
2. Does every function do exactly one thing?
3. Is there anything "just in case" that isn't used yet? Delete it.
4. Could this be simpler and still work? If yes, it's not done yet.
